# Momcozy GEO 试点：排期与资源讨论稿

> **状态：L0 讨论基线（方法），2026-11-08。** 用户同意方案 A：先建立依赖驱动的排期框架，不承诺绝对日期、不编造人数或预算、不承诺 SLA。本稿只给相对顺序、前置条件与待补输入；不是排期承诺或资源批准。

## 1. 为什么不用日期倒排

PMO 页面 Wave 3 为 2026-11-24～12-26，但能力截止日存在两组互相冲突的记录（项目卡 vs 2026-11-03 变更留痕）。在权威版本未确认前，任何倒排日期都是伪精确。更关键的是：关键路径上有多个**外部等待项**，加人无法缩短。

因此本稿只回答三个问题：什么必须先发生、谁能让它发生、什么情况下必须改范围。

## 2. 里程碑的前置条件

| 里程碑 | 可开始的最小条件 | 谁能让它成立 | 当前状态 |
|---|---|---|---|
| M0 范围与资产核验 | 业务 owner 就位；PMO 只读范围明确；候选提名有责任人；市场/ASIN/入口与预算 owner 明确 | 业务负责人、PMO 数据 owner、品类 owner、预算 owner | AUTH-02/03 已同意，均待落实 |
| M1 需求与设计冻结 | M0 关闭；需求、样本协议、权限与数据权利矩阵、复用评估与 ADR 草案经评审 | 业务/产品 owner、数据 owner、技术负责人 | 未开始 |
| M2 纵向切片 | 隔离测试应用就绪；样本来源合法（或明确仅用合成数据）；开发与部署授权；身份与权限模型确定 | 飞书管理员、项目负责人、技术负责人 | AUTH-01 已同意，其余未授权 |
| M3 六能力闭环 | M2 通过；测量轨道许可（消费端采样，或经批准的替代轨道/导入）；预算批准；事实 owner 可用 | 法务/平台 owner、业务 owner、商品 owner、预算 owner | 均未成立 |
| M4 试点交付 | M3 验收；生产资源与发版审批；备份恢复演练；UAT 签收人明确 | 业务 owner、运维、管理员 | 未开始 |
| M5 运营扩展 | 试点被接受；成本可持续；扩展范围与真实使用数据授权获批 | 业务负责人、预算 owner、数据 owner | 未开始 |

表中“可开始”不等于“已批准启动”；“已同意”不等于“已落实”。M0 的纸面预研可先行，但里程碑启动仍需 PMO 只读范围与 AUTH-03 提名责任人落实。

## 3. 关键路径与并行度

**建议的关键路径（串行）：**

```text
M0 资产与范围核验
  → M1 需求/协议/权限冻结
    → M2 窄切片（受开发部署授权约束）
      → M3 闭环（受采样许可与预算约束）
        → M4 UAT 与签收
```

**可并行（不依赖前一项完成）：**

- AUTH-01 结构验证准备 与 AUTH-02 元数据核验可同时推进，但都需要各自 owner 先落实。
- 复用评估的纸面部分（Main 公开页面、飞书官方文档）不依赖内部授权。
- 验收单元与运营指标口径的细化，可在 M0 期间完成。

**不能并行：** 同一 owner 承担的多个事项（例如同一位数据 owner 既批 PMO 范围又批 BrandOS 范围），在排期上必须视为串行，不能假设“两边同时开工”。

**“已发起”不等于“已完成”：** 外部等待一旦发起申请，就应在记录中标注为“审核中”，不得计入任何里程碑的完成条件。实际关键路径取各外部等待中“最晚确认时间 + 其后续串行工作”的最大值，而不是简单相加或取最初发起时间。

## 4. 外部等待项（团队不可加速）

| 等待项 | 性质 | 未到位时的处理 |
|---|---|---|
| 飞书管理员审核与发版 | 平台与组织流程 | 只做纸面与入站设计，不进隔离验证 |
| Perplexity 适用协议与法务判断 | 法律判断 | 采样保持 HOLD，不改用人工或替代入口绕过 |
| PMO/BrandOS 数据 owner 授权 | 组织决策 | 只做公开页面层面的 C 级观察 |
| 商品事实与身份映射批准 | 业务审核 | 涉及 ASIN 的内容与判真保持 unknown |
| 商品声明合规审核 | 健康、安全、疗效、报销/保险、监管及母婴适用声明 | 对应声明不做、不批准，其他内容不受连带 |
| PMO 权威日期版本确认 | 信息核对 | 不排绝对日期 |
| 预算与成本上限 | 业务决策 | 不调用付费服务，不给成本结论 |

这些项目不因“加人”或“加班”缩短；排期应把它们作为显式等待节点，而不是隐藏缓冲。

## 5. 资源类别（不给人数）

| 类别 | 用途 | 是否首期必需 |
|---|---|---|
| 业务/产品 owner | 范围、优先级、UAT 签收 | 必需 |
| 数据 owner | 资产范围、逐用途权利 | 必需 |
| 商品/渠道事实 owner | 身份映射与事实批准 | 必需（涉及商品声明时） |
| 技术与集成 | 架构、ADR、实现与运维 | 必需（M2 起） |
| 设计与前端 | 工作台与交互 | M2 起 |
| 飞书管理员 | 应用、权限、发版 | M2 起 |
| 合规/法务 | 健康、安全、疗效、报销/保险、监管及母婴适用声明；平台条款 | 按声明类型触发 |
| 预算 owner | 成本类别、额度上限与停止条件 | 必需（M0 起识别，M3 前批准） |
| 业务 UAT 与合规签字 | 验收与签收；独立验收检查器是否设置待定 | M4 起 |

同一人可承担多个角色，但**审核独立性不能合并**：执行人不能给自己签发验收。具体人员、工时与预算待业务与人事 owner 确认。

## 6. 范围削减选项

若时间或资源不足，建议按以下顺序削减，保留最小闭环：

1. **先减广度**：ASIN 数量、市场、平台轨道维持在最小可行集合。
2. **再减能力**：内容生成与复测报告可先维持纸面与合成样例，不进入真实闭环。
3. **再减自动化**：定时、卡片按钮、自动派单全部延后，保留人工发起。
4. **不减的部分**：权限与审计、状态守恒、失败与 unknown 区分、证据可追溯。这些是正确性底线，削减后结果不可信。

## 7. 给出绝对日期前必须到齐的输入

1. PMO 权威日期版本（哪一组为准，或明确以本项目计划为准）。
2. 业务 owner、数据 owner、商品 owner 的可用性。
3. 飞书管理员审核与发版所需时间。
4. 采样许可与法务判断的预计结论时间。
5. 预算上限与成本口径。
6. 团队实际可投入的角色与时段。

缺任一项时，只能给相对顺序与条件性表述（例如“在 X 到位后约需完成 Y 的前置工作”），不给日期。

## 8. 条件性承诺的写法

建议区分三种表述，避免混淆：

- **可承诺**：不依赖外部输入、团队内部可控的产出，例如“起草 T1–T3 表格模板”“整理负例清单”。纸面记录仍标 L0；未运行不得标 L1，设计冻结与验收不在此列。
- **条件性**：依赖外部输入，例如“在 PMO 范围确认后启动 M1”。
- **不可承诺**：涉及平台许可、法律判断、业务效果的部分，例如“何时可开始真实采样”“品牌提及是否提升”。

PMO 若要求固定窗口交付，应把上述分类原样呈现，而不是把条件性事项写成确定承诺。

## 9. 决策点

| 决策 | 决策人 | 触发时机 |
|---|---|---|
| 是否以 PMO 窗口为硬约束 | 业务负责人 | M0 期间、排期之前 |
| 是否扩大数据授权至 BrandOS | BrandOS 数据 owner | M0 期间 |
| 是否批准 Main 代码只读评估 | Main owner 与本项目负责人（技术负责人出评估意见） | M1 前 |
| 是否批准开发与部署 | 项目负责人 | M2 前 |
| 测量轨道采用消费端采样还是批准替代轨道 | 法务/平台 owner + 业务 owner + 项目负责人 | M3 前 |
| 是否批准真实内容生成与内部候选任务 | 内容/商品 owner + 项目负责人 | M3 阶段，分别授权 |
| 范围削减方案选择 | 业务负责人 | 任一外部等待超期时 |

## 10. 本稿不做什么

不排绝对日期、不给人数与预算数字、不承诺交付周期或 SLA、不把 PMO 页面记录当作承诺、不把 AUTH-01/02/03 扩大为开发或采样授权、不预设技术栈。
