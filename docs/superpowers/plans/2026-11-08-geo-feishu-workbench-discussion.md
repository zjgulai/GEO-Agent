# Momcozy GEO 试点：飞书与工作台交互讨论稿

> **状态：L0 讨论基线（部分），2026-11-08。** 用户已同意本稿第 2 节的三项边界作为讨论基线：群回执不按权限或结果显示差异；链接鉴权不能保护已出现在群消息、卡片或通知预览中的内容；私聊不是天然安全通道。其余分工、情景、待决项和实施仍为建议，不是实施设计或接入授权。此前同意的诊断候选人工确认/驳回、内容草稿人审和复测报告方法不等于批准飞书按钮、通知、真实任务、接口、开发或任何发布。当前没有连接或配置飞书应用。

## 1. 首期分工建议

| 入口 | 建议职责 | 披露与动作边界 |
|---|---|---|
| 群内 @ | 提供交互入口；在群和内容获准时使用统一、中性回执或通用工作台入口 | 将回复可能面向多名群成员、历史受众及通知预览作为安全设计假设，具体行为待平台与群配置实测；不因提问人有权就展示业务结果或证据。是否回执及其措辞需按群风险确认。 |
| P2P 私聊 | 支持用户主动查询；在收件人身份、用途、可见内容及发送权限成立时返回适当信息或工作台入口 | 不把私聊视为天然安全；项目名、对象类型、标题、计数、正文、通知预览和链接都可能有敏感性，按权限与渠道披露规则决定，而非默认全文展示。P2P 发送失败不转发至群。 |
| 工作台 | 在获授权的受众范围内展示项目、数据及依据；承载较复杂的诊断、候选和草稿审阅 | 按服务端身份、租户、项目、对象、动作及用途授权；个人请求与项目共享对象的可见范围分别定义。实际功能、角色、工作台身份接入及审核操作的实现均待评审与授权。 |

这是产品分工，不排除未来按批准规则使用飞书卡片；**候选确认/驳回的产品方向已获同意，具体在哪里操作、是否提供飞书按钮尚未确定**。工作台审阅通过也不自动创建或分派真实任务、外发或发布。

## 2. 受众与权限：不只检查提问人

1. 用户在群内输入的原问题本身可能暴露信息；机器人无法通过后续安全回执消除已发出的文字。应引导用户避免在群中输入受限资料，群是否适合承接请求须先评估。
2. 群中的回执、卡片、链接、预览、引用、文件名及通知显示内容都可能暴露元数据。是否展示按实际群设置、接收人及适用数据规则评估；不能仅依赖“详情链接要登录”来保护已发出的摘要。
3. 未授权与获授权请求若在群内分别显示“无权限”和“已受理”，可能暴露用户权限或对象存在性。若允许回执，建议采用不区分权限及处理结果的中性文案，且仅表示收到、并不承诺处理；如“请求存在”本身敏感，可不在群内回执。具体交互和允许的元数据待评审。
4. 对私聊和工作台，身份、项目、对象和用途都要授权；群成员身份或 App 管理员身份不自动获得项目数据权限。具备相应权限的群成员仍可作为独立用户访问获准对象，不因为其在群里就一概拒绝。
5. 链接只提供导航，不替代服务端授权；未授权用户看到的响应、页面标题及链接预览不应无意暴露对象存在性。群内优先讨论中性的通用入口，对象级链接及预览行为待实际环境审查；不预设存在一次性链接或卡片能力。
6. 排队处理、交付和后续读取时应考虑权限变化；权限被撤销后不继续提供受影响的数据。已发送消息不假设一定可撤回；必要的历史保留或删除按数据 owner 和适用制度处理。

## 3. 交互情景（全部为未来设计示意）

- **无可判断数据：**在获准访问的工作台视图中显示“暂无可判断数据”，区分未执行、失败和指标 unknown；群内不因该请求默认披露无数据状态，更不能写成品牌未被提及。
- **授权用户请求已有结果：**群内仅按获准规则给中性回应或不回应；用户在工作台经授权查看结果与口径。用户通过 P2P 主动查询时，具体返回范围按该用户、用途和数据权限决定。
- **人工审阅内部候选：**有权审阅的人在确定的审阅入口查看观察、依据、假设和建议，确认或驳回；不把该决定说成任务已分配、已执行或已发布。飞书按钮和通知均未确定。
- **权限撤销或结果交付失败：**停止向无权受众交付受影响信息；不向群补发私聊结果。发送结果不确定时需核对回执/状态，不能盲目承诺“恰好一次”或持续重发。

以上未创建请求、候选、消息或真实样本；是否产生审计记录和持久任务是未来实现设计问题，而不是当前已发生的动作。

## 4. 长连接与可靠性：已研究约束和待验证设计

本地[第一手研究笔记](../../research/2026-11-08-geo-first-party-research.md#3-飞书长连接事件订阅机器人权限上线)记录了 2026-11-08 对飞书官方文档的只读研究；本轮未重新访问文档：

- 【B：转引官方文档】长连接事件订阅面向企业自建应用；接收群 @ 和 P2P 消息分别涉及所需权限。当前应用类型、权限、可用范围及管理员审批均未知。
- 【B：转引官方文档】事件处理有平台时限和可能重复投递；对 `im.message.receive_v1` 应按该事件文档使用 `message_id` 做业务去重。其他事件依其文档选择标识，不假设所有事件同键。
- 【C：建议】耗时处理与事件接收解耦，持久化、重试、去重、出站回执及“不确定”状态需形成可审查的可靠性设计；具体队列、数据库或运行框架未选定。去重和 outbox 也不天然保证远端恰好一次。
- 【C：待验证】消息事件与卡片交互回调分别核验订阅、权限、时限、可靠性和动作授权；不把消息事件的重试机制自动套到卡片回调。是否做卡片按钮仍未批准。

## 5. 后续设计和验证的待决项

- 飞书群和 P2P 的拟定受众、可显示字段、是否允许回应/通知及隐私策略；各群的管理人、成员和历史可见性。
- 真实身份映射、工作区/项目/对象授权、个人与项目共享结果的区别，以及拒绝、撤销、重试、重复点击和发送不确定时的界面。
- 官方 SDK 与回调最新文档、应用类型、应用可用范围、订阅权限、测试环境和出网条件；应用参数、管理员及具体环境均待授权核验。
- PMO/Main 现有资产、契约和服务是否可在获得授权后复用；技术选型、审阅入口、架构及具体验收标准未冻结。
- 获授权后先用合成数据验证群受众泄露、私聊预览、越权链接、权限撤销、重复事件和发送不确定等正反场景，再依项目授权安排真实接入；合成检查不证明真实环境安全。
